# Datasource 与 Sensteed 财务插件逐页复审

审查日期：2026-10-18。结论：入口分组和部分核心表单已经收敛，但两端尚未达到同一产品的行为一致性。下一轮应优先解决统计口径、筛选生效、业务对象定位和完整任务能力，再处理布局。

## 1. 范围与证据边界

- 网页基线：`datasource.dofe.ai@63f8778330888d5fa0a904e124990dc454804539`。
- 插件初始基线：`docker-helm.dofe.ai@ac28ef0a`；交付前复核到 `e20608ee`。期间并行提交 `5117d35b` 已改善分析技能与分析指令的年度/主体 ID 携带，报告已纳入该进展；导航、经营分析、预算、审核和 BOM 的上述问题实现未改变。检查覆盖 `plugins/dsh-sensteed-finance/src/`、宿主代理和公开路由，不把源码注释中的“已对齐”当作结论。
- 逐一清点了 `apps/web/app/[locale]` 下 **29 个页面入口**：25 个独立业务页面、2 个兼容入口、2 个登录相关页面。插件可识别其中 **24/25 个独立业务目的地**；缺少费用类别。
- 本轮证据是页面组件、路由解析、表单与请求调用链的源码对照，以及实际函数的受控执行。线上目标为 [Datasource](https://ds.hozonauto.com)，浏览器业务会话停在 SSO 登录页；新开访问还发生导航超时。因此**没有完成生产业务页面逐页点击、真实角色与真实数据验收**，也未确认运行中的桌面插件等同于上述源码版本。
- `npm run check:datasource` 通过，但它固定列举 24 个目的地，并未从网页目录反向检查遗漏，也没有覆盖下文中的完整行为。
- 机器可读记录见 [路由清点与模拟数据证据](./page-by-page-audit-20261018.evidence.json)。其中金额均为模拟数据，未使用真实账务数据。

## 3. 优先整改项与可复核证据

### R1 · 经营分析和工作台的“同名数字”不是同一口径（P1）

插件 `src/views/operations.js:27` 将缺失实际收入/支出累计为 0；`:50` 又用实际值→计划值→0 回退绘图。网页 `operations-section.tsx:69` 分别维护计划和实际完整性，`:97` 检查实际值，`:137` 缺失显示“—”。

受控执行原 `OperationsView`：计划收入 200、计划支出 50、实际收入缺失、实际支出 80。插件实际净流入 KPI 为 **−80**，月度净额图为 **+120**；网页源码分支应显示实际净额 **—**、计划净额 **150**。这是两端差异，也是插件同页自相矛盾；此例不是生产事故统计。

插件 `overview.js:27` 用开放活动列表数量当待填报，网页 `workbench-todo-card.tsx` 使用角色对应的审核队列汇总或个人指派汇总。插件 `overview.js:59` 的第五张卡是预警数量，网页 `overview-section.tsx:130` 附近则按范围展示 PR 台账/预算健康。插件也未消费预算未发布提示。

整改验收：统一指标名称、正式版本、分母、数据缺失规则及角色待办定义；未知不替换成零，计划不回填实际；不能用最多 100 条活动列表长度代表全部待办。对零值、缺失、未发布预算、部分接口失败分别验收。

### R2 · 预算执行筛选、月度及分页不符合页面所示范围（P1）

- `src/views/budget.js:25` 的筛选是单值，且初始化 `unassigned: false`；网页 `budget-section.tsx:120` 起支持 `orgs/depts/expenses/months` 多值与未分配。
- 插件头部只在 overview/operations/cash/alerts 显示主体选择，预算页没有主体选择；`shell.js:130` 又只从 drillParams 取预算主体。因此用户通过普通入口无法完成同等主体筛选。
- `index.js:243` 的 `/budget` 代理只将 month/expenseType 传给明细，汇总未接收这两项；插件 Matrix/Variance 直接使用 summary，没有网页 `budget-section.tsx:219` 的费用/月度过滤。筛选明细与汇总可能得出不同范围。
- `budget.js:108`、`:173` 的矩阵点击只带 month，丢主体/费用/部门。网页 `budget-section.tsx:498` 起保留行维度与未分配状态。
- `MonthView`（`budget.js:181` 起）内部默认本月，未使用 drillParams/filter 的 month；头部月份与内部月份可不一致。上游图表点击“某月”不能保证显示该月。
- 明细请求用 `BUDGET_LINE_LIMIT=200`（`head.js:51`、`budget.js:55`），`LinesView` 的 Pager 却用 `PAGE_SIZE=20`（`budget.js:237` 附近）。总数 201 时实际只需 2 页，界面会算 11 页，后续出现空页。

整改验收：一个规范化筛选对象驱动汇总、图表、明细、保存视图和分页；直接选择主体；矩阵单元格携带完整行维度；月度组件以同一月份状态为准；分页使用实际请求 limit。至少覆盖 0/20/21/200/201 条和多维筛选。

### R3 · 到达页面不等于定位到同一个业务对象（P1）

- `navigation.js:80` 起未解析预算多选筛选、未分配与预算明细 page；实际函数探针确认这些参数被丢弃。
- `navigation.js` 不读取全面预算的 `version`，`engine.js:3` 也从空版本开始；网页 `budget-engine-console.tsx:147` 使用 URL 版本。
- `/review?task=…` 虽解析成 taskId，但 `review.js:12` 的列表未添加它；网页 `review-section.tsx:190` 添加 taskId。通知到指定活动审核时插件会展示更大的队列。
- `alerts.js:61` 的源数据目标只含页面类型和空参数；网页 `alerts-section.tsx:99` 起根据预警携带年度、主体、月度或未分配。
- `overview.js` 的指标/月份下钻未传当前主体；`shell.js:130` 的预算却不继承头部 orgId。某主体总览点进去可能变成全主体预算。

整改验收：按“页面 + 年度 + 主体/未分配 + 版本 + 月份 + 部门/费用 + 任务/记录”定义业务目的地，参数由目的地明确消费。普通入口可以重置范围，对象链接必须恢复范围；无效链接提示不可用，不得默默放宽筛选。建立真实点击后的请求断言，不能只测解析函数返回非空。

### R4 · 旧入口与版本职责仍未迁移完成（P1）

网页 `legacy-budget-view-redirect.tsx:18` 将 `snapshot-compare/year-compare/versions` 迁入三个独立比较页面。实际执行插件解析函数：前两者落入 budget 默认页，versions 仍落旧页签。`budget.js:4` 保留第八个版本页签，网页 `budget-section.tsx:256` 起仅有七个执行页签。

整改验收：网页旧链接、插件旧通知、菜单和保存视图都迁往相同的独立目的地；移除插件重复的版本管理职责。原参数沿用，未知 view 明示错误。插件保存视图也要兼容网页 query 命名，当前插件读 expenseType/versionId，网页使用 expense/expenses/version 等 URL 字段，不能直接互认。

### R5 · 无预算版本时，插件缺少从零开始的路径（P1）

网页 `budget-versions-view.tsx:134` 提供“新建预算草稿”。插件 `comparisons.js` 只提供比较和月结快照；`budget.js:517` 的版本管理仅有对既有版的确认/发布/锁定/复制；`engine.js` 要先选既有版本才能滚动创建。

整改验收：年度没有版本时，具备权限的财务人员可在相同入口创建首版草稿，随后去填报活动或全面预算；非写入者看到原因和下一步。版本清单、创建、生命周期动作与比较在两端保持一致的归属。

### R6 · 比较页缺少一致的默认选择和解释（P2）

网页 `budget-snapshot-compare-view.tsx:49` 默认最近两份不同快照，`:142` 起区分 0/1/多份；插件 `comparisons.js:4` 两侧空选，未排除同一 ID。网页 `budget-year-compare-view.tsx:56` 自动选版本，`:90` 提供覆盖率；插件年度比较缺少这些信息及行差额率。

整改验收：相同默认 A/B，快照不足时不给出误导性的零差异；版本选项统一名称、年度、类型、状态、主版本；解释冻结月份与年度未分月金额；正式对比和试算明确分开。无需强行让三页拥有完全相同字段。

### R7 · 资金主流程已接近，仍缺一致的汇总到计划路径（P2）

网页 `cash-month-summary.tsx:69` 的指标指向含年度、主体、月份的付款/收入计划。插件 `cash.js:137` 的汇总 KPI 没有点击动作，且汇总区域未呈现网页 `cash-section.tsx:204` 的 computed 口径说明。

整改验收：当月计划/实际收入、支出都可到相应清单，原范围保留；余额/剩余金额不可用时说明来源局限。保留已经实现的严格缺失值处理、排款金额比例联动、币种证据和调整重试，不重复推倒重做。

### R8 · 填报与复核仍在使用通用表格替代业务步骤（P2；task 定位见 P1 R3）

网页 `filing-console.tsx:135` 分待办阶段，`:1184` 提供版本历史，`:1610` 有普通填报 Excel 导入；插件 `filing.js` 复用同一指派表，历史由 `FinanceEvidence` 展开，`entry.js:257` 的普通 AssignmentDialog 仅逐行编辑。不要与已经有 Excel 的预算逐条审核混为一谈。

整改验收：个人任务优先给截止、可否填写、被退回原因和下一步；普通填报补模板/预览/导入/行错误；历史明确当前有效版本与被替代版本；复核前展示对象、范围、行数、金额和影响，批量动作显示逐项回执；不把“已读/已提交”写成“完成/正式入账”。

### R9 · 数据中心的信息架构和数据规模指标不统一（P2）

网页 `data-center-section.tsx:29` 统计业务数据资产并给出明细入口，插件 `datacenter.js:77` 起显示质量问题、最近最多 20 条同步、已加载批次数；这些不是相同指标。来源记录网页嵌在数据中心，插件拆一级导航。预算事实网页嵌在预算执行，插件另放 facts 一级入口；付款/计划事实组件文件存在不代表当前页面已挂载，不能据文件名判定功能可达。

整改验收：统一“数据资产→采集来源→暂存记录→核对发布→正式事实”的位置和术语；最近 N 条必须写明窗口，完整规模使用服务端 total；源币种/单位不藏进详情；在同一对象之间提供双向追溯。来源独立页可以保留，但网页和插件必须有一致的主入口与上下级关系。

### R10 · 费用类别维护存在漏页（P2）

### R11 · 预警加载失败与“无风险/规则未确认”混在一起（P1）

`alerts.js:23` 起汇总错误设置 `{}`，规则错误设置空列表，统计又回退 0；列表查询没有取消或序号校验。快速切换筛选时，较早请求可能覆盖较新结果。

整改验收：汇总、规则、明细分别有加载/错误/重试；规则读取失败禁止呈现“尚未确认”的业务结论；请求结果必须绑定当前年度、主体和筛选。保留失败前数据时显示过期标记，不显示成当前范围结果。

### R12 · 身份页仍混用旧联系人与权威身份模型（P1 / P2）

网页 `feishu-directory-card.tsx:34` 使用 `useFinanceOrganizationDirectory`，按 identityEnabled/enabled 判断身份就绪；插件 `entry.js:48` 使用 `/contacts?limit=100`，`:370` 的 MapUserDialog 让用户手输 userId。插件成员授权页已经使用权威目录，导致插件内部两套选人认知。

整改验收：通讯录、岗位分配、数据授权以同一 SSO 组织身份与同步状态为依据，人员无需登录后才可选；手工技术 ID 迁出普通业务流程。不要通过放宽服务端身份规则追求前端一致。

权限编辑主流程已收敛，但网页 `permission-center.tsx:120` 起提供历史补充授权查阅/撤销；插件 `permissions.js` 未提供。补齐独立、明确不参与当前权限计算的审计区域，数据范围优先显示主体/部门名称，技术 ID 留作追溯。

### R13 · 成本工程存在任务能力缺口，不能只改名（P1）

网页 `ce-console.tsx:113` 提供 EBOM Excel 上传；`ce-ebom-workbench.tsx:45`、`:276`、`:285` 提供成本预测 Excel 下载、AC 目标和采购信息；`ce-console-advanced.tsx:286` 的报价支持预览并明确应用到预测。

插件 `bom.js` 主要是逐行/JSON 导入、估算、反算、变更、报价登记及导出批次回写；没有上述完整工作流。报价表单还缺有效期，币种非必填，本地价格校验不等同网页的 Zod 校验（正数、最多四位小数）。插件把“导出批次创建/手填文件引用”作为终点，也不等同下载业务文件。

整改验收：两端统一为“成本工程”业务域；EBOM 文件上传→预览行错误→确认导入→维护单价/目标/采购→报价应用预览确认→下载预测文件完整可达。保留 JSON 为高级入口；审批态与字段校验同契约。该项应单列完整交付，不宣称已有读写接口即功能齐全。

### R14 · 助手和通知的同名入口仍有不同操作预期（P2）

网页 `assistant-section.tsx` 是基于预算/资金/质量数据的有限意图核对，不应宣传成无限制 AI 推理。插件 `analyze.js` 选择技能后创建会话并关闭面板；并行提交已让分析指令携带年度与主体 ID。剩余优化是两端明确“数据核对问答”和“发起深度分析”两种动作：前者就地给证据，后者去会话，保留范围并提供返回业务目标，失败时留在原上下文。

网页 `notification-center.tsx` 打开业务前标已读；插件 `notifications.js:20` 的查看动作仅导航。统一为打开后标已读，保留单独标已读与“已读不等于业务完成”说明；标记失败不应让业务入口不可用。分类统一为“待我处理 / 与我有关 / 系统提醒”。

## 5. 网页也需要优化，不能直接作为无条件模板

- **W1：零金额不等于项目缺失。** 两端年度比较都以 baseBudget/targetBudget 是否为 0 分“可比/单侧”。真实零预算与不存在须由服务端存在性字段区分；调整后同步可比总额、覆盖率与变化率。当前属于共同逻辑风险，不是插件独有差异。
- **W2：通知完整性。** 网页请求 limit=50 且没有分页；插件已有分页。应为网页增加完整列表访问能力，统一真实总数和未读数，不能为了视觉一致删除分页。
- **W3：记录上限。** 两端部门归属都有已加载记录限制；网页部分普通填报/审核清单也使用固定 limit。需逐类采用 total 与分页/加载更多，局部排序明确只作用于已加载范围。
- **W4：确认方式。** 网页仍存在 window.confirm/window.prompt，插件又使用通用空表单，建议共同收敛为带业务摘要、明确动作和原因的确认组件。
- **W5：表单基础规范。** 未保存退出、首错聚焦、读屏字段关联、长内容和键盘操作应作为共同规范，不把字号和颜色一致当作完成。390/768/1024/1440 宽度及键盘检查属于下一轮实际交互验收，本轮没有对全部页面逐尺寸重测。
